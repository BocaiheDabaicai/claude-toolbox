# 交付循环

## 1. 切片选择

一个垂直切片应满足：

- 端到端：页面/接口/数据都能跑通；
- 可演示：业务能看懂；
- 有验收标准；
- 依赖少，能在一周内完成；
- 不跨太多模块。

示例：

```
S1：登录 -> 客户列表（只读）
S2：新建客户 -> 列表刷新
S3：编辑/软删客户
S4：搜索/分页/导入
```

不要按“先做所有表、再做所有接口、再做所有页面”横切。

## 2. Definition of Ready

功能点进入 `in-progress` 前：

- 范围明确；
- acceptance 可验证；
- 依赖已完成或可 mock；
- owner 确定；
- 需要的接口/数据/权限已确认。

## 3. Definition of Done

功能点进入 `accepted` 前：

- 代码完成；
- 主链路/异常态验证；
- 验收证据；
- 文档/台账更新；
- 验收人确认。

## 4. 每日

15 分钟：

- 昨天完成什么；
- 今天做什么；
- 有什么阻塞；
- 需要谁决策。

完成后：

- 更新 `features.csv` 状态；
- 追加 `delivery-log.md`（如果有决策/变更/阻塞）。

## 5. 每周演示

演示脚本：

1. 用真实数据/接近真实数据；
2. 从用户视角走主链路；
3. 展示空态/错误态；
4. 说明已知限制；
5. 记录反馈 → features/roadmap。

演示后：

- 新需求进 `features.csv`（idea/scoped）；
- 变更更新 roadmap；
- 决策写 decisions。

## 6. 阻塞

- 当天记录，不埋在脑子里；
- 明确阻塞类型：业务决策/数据/权限/第三方/技术；
- 指定负责人和截止时间；
- 阻塞超过 2 天升级。

## 7. 范围变更

流程：

1. 记录变更请求（delivery-log）；
2. 评估影响：功能点、切片、时间、风险；
3. 决定：接受 / 延期 / 砍掉；
4. 更新 features/roadmap；
5. 影响架构的写 decisions；
6. 通知干系人。

不要“先做了再说”。

## 8. 里程碑

- 每个里程碑有明确目标和验收人；
- 里程碑内只做 P0/P1；
- 里程碑结束做一次验收和复盘；
- 未完成功能点不要偷偷带进下一个里程碑。

## 9. 交接前

- features 状态准确；
- roadmap 下一次开工步骤明确；
- handoff 填完整；
- 验收记录归档。
