# 交付模型

## 1. FDE 是什么

Forward Deployed Engineer：贴着业务现场，把模糊需求变成能跑的系统。特点：

- 离业务近，反馈快；
- 端到端负责，不只写某一层；
- 用可运行的系统对齐认知，而不是用长文档；
- 交付完要能交接，不是个人英雄主义。

## 2. 和传统项目的区别

| 传统 | FDE |
|---|---|
| 需求冻结后开发 | 小步确认、持续校正 |
| 按模块交付 | 按垂直切片交付 |
| 文档先行、代码后行 | 文档与代码同步，文档是契约 |
| 上线才算完成 | 演示 + 验收 + 交接才算完成 |
| 变更走重流程 | 变更可见、可评估、可记录 |

## 3. 核心原则

1. **可演示优先**：每个切片都能给业务看。
2. **范围显式**：写清楚做什么、不做什么。
3. **一个事实源**：功能点状态只看 `features.csv`。
4. **决策留痕**：选了什么、为什么、代价是什么。
5. **验收有证据**：截图/录屏/测试/对账。
6. **交接可运行**：接手人按文档能跑起来。
7. **知识回灌**：项目经验变成 Skill 的规则/模板/脚本。

## 4. 角色与决策权

| 角色 | 决定什么 | 不决定什么 |
|---|---|---|
| 业务负责人 | 做什么、优先级、验收标准 | 技术实现 |
| FDE/开发 | 怎么做、技术选型、切片拆分 | 业务优先级 |
| 验收人 | 是否通过验收 | 需求范围 |
| 运维/DBA | 环境、发布、回滚方式 | 业务规则 |

原则：**业务决定 What，FDE 决定 How，验收人决定 Done。**

## 5. 节奏

- **每日 15 分钟**：昨天做了什么、今天做什么、有什么阻塞；
- **每周演示**：给业务看可运行切片，收集反馈；
- **里程碑验收**：按 `acceptance.md` 逐项验证；
- **项目结束复盘**：回灌 Skill。

## 6. 沟通

- 重要结论写进 `delivery-log.md` / `decisions.md`；
- 不用“我以为”“口头说过”作为依据；
- 风险早说，不要等到截止日；
- 变更先评估影响，再决定做不做。

## 7. 反模式

| 反模式 | 后果 | 替代 |
|---|---|---|
| 大爆炸式开发 | 很久看不到结果，返工大 | 垂直切片 |
| 需求只在聊天里 | 遗漏、扯皮 | features.csv |
| 所有功能都 P0 | 没有优先级 | P0/P1/P2 + 里程碑 |
| 文档事后补 | 与实现不一致 | 文档即契约 |
| 没有 Non-goals | 范围膨胀 | brief 写清楚不做什么 |
| 个人英雄 | 无法交接 | 文档 + 运行手册 |
| 变更不记录 | 无法追溯 | delivery-log + decisions |
| 验收靠感觉 | 争议 | 可验证的 acceptance |
